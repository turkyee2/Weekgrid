## 1. 미해결 결정 (논의 중)

### 1.1 시간 입력 단위 — 1분 vs 5분
- **현재 상태**: 1분 단위 (시/분 드롭다운, 분 00~59).
- **고민**:
  - 1분: 정밀하지만 분 드롭다운 옵션이 60개라 길다.
  - 5분: 빠르고 짧지만 `14:37` 같은 값은 못 넣는다.
- **후보 대안**:
  - (a) 분을 텍스트로 직접 입력 허용 + 검증
  - (b) 5분 기본 + "직접 입력" 토글로 미세조정
  - (c) 자주 쓰는 프리셋(00/30) 빠른 버튼 + 드롭다운 병행
- **결정**: 보류. 실제 사용 패턴 보고 결정.

### 1.2 지난 미완료 항목 처리 (2026-08-06 논의 시작)
- **문제**: 날짜가 지났는데 완료되지 않은 항목이 그 날짜 셀에 그대로 남아
  묻힌다. "다시 보여주거나 별도 표시" 또는 "다른 날짜로 이동"이 필요해 보임.
- **고민할 지점**:
  - 표시만 할지(예: 매트릭스에 "지난 미완료 N건" 배지, 별도 사이드 패널)
    vs 실제로 데이터를 이동시킬지(날짜 재할당) — 후자는 "그 항목이 원래
    언제 계획됐었는가" 기록을 잃는 트레이드오프가 있음.
  - 이동한다면 자동(예: 오늘로 매일 굴려줌)인지 수동(사용자가 드래그/버튼으로
    옮김)인지 — 자동은 "왜 계획이 계속 밀리는지" 인식을 방해할 수 있음.
  - 반복 항목(아직 미구현, 7-B)과 개념이 겹칠 수 있어 그쪽 설계와 같이 고려.
- **결정**: 보류, 추가 논의 필요.

### 1.3 회원가입·계정 관리 보안 강화 (2026-08-06 논의 시작)
- **문제 의식**: 지금은 Supabase Auth 기본 이메일/비번 가입 흐름만 쓰고
  있고, 실서비스 수준(비밀번호 정책, 이메일 인증 강제, 세션/기기 관리,
  비번 재설정 흐름, rate limiting 등)을 점검한 적이 없음.
- **다음 단계**: 우선 Supabase Auth 대시보드 설정(이메일 인증 필수 여부,
  비밀번호 최소 강도, rate limit 등)을 현황 점검부터 하고, 부족한 부분을
  추려서 항목화. 커스텀 서버 코드가 필요한지(예: 추가 검증)는 점검 후 판단.
- **결정**: 보류, 현황 점검 필요.

### 1.4 피드백 확인 방법 — 관리자 계정 vs 대안 (2026-07-27 논의 시작)
- **현재 상태**: `feedback` 테이블 select/insert 정책이 `auth.uid() = owner_id`뿐이라,
  본인이 남긴 피드백만 본인 계정으로 조회 가능. 운영자(개발자)가 다른 사용자의
  피드백을 앱 안에서 볼 방법이 없음.
- **후보**:
  - (a) **당장·무료**: Supabase 대시보드 Table Editor에서 `feedback` 테이블을
    직접 확인 (대시보드는 RLS를 우회하는 관리 세션이라 전체 행이 보임). 코드
    변경 0, 지금 바로 가능.
  - (b) **가벼운 앱 내 조회(추천)**: `feedback` select 정책에 본인 UID 예외를
    추가(`auth.uid() = owner_id or auth.uid() = '<내 UID>'`) + 설정 탭에 본인
    UID일 때만 보이는 "피드백 보기" 섹션 추가. 새 역할/테이블 없이 정책 1줄 +
    작은 목록 컴포넌트로 해결.
  - (c) **역할 테이블**(`admin_users` 등)로 정식 관리자 개념 도입 — 지금
    규모엔 과함, 비추천.
  - (d) **알림형**(피드백 insert 시 이메일/슬랙으로 통지) — Database Webhook +
    Edge Function 필요(서버 코드 최초 도입 명분). 지금 단계엔 오버킬.
- **결정**: (b) 채택, 구현 완료(2026-07-27). 리터럴 UID를 public 레포에 커밋하지
  않기 위해 처음엔 `current_setting('app.admin_uid', true)` 세션 GUC로 구현했으나,
  Supavisor 커넥션 풀러가 기존 커넥션을 재사용해 새 GUC가 반영 안 되는 문제
  (관리자 계정에서도 피드백 0건으로 보임)를 발견 → `app_settings` 테이블 +
  `is_admin()` security definer 함수로 교체(매 쿼리마다 실제로 읽으므로 풀링과
  무관). 실제 값은 `app_settings` 테이블과 `VITE_ADMIN_UID` 환경변수에만 존재.
  `handoff.md` 2장/7장 참고.

## 2. 낙서장 발전 로드맵

현재 낙서장 = 목록 + 제목/본문 편집 + 저장/삭제 (최소 형태). 단계적으로 확장.

- **1단계 — 탐색·정리 (저비용, 즉효) — 완료(2026-08-06)**
  - 검색: 제목·본문 키워드 필터 (클라이언트 필터, 서버 변경 없음)
  - 정렬 옵션: 최근 수정순 / 제목순 토글
  - 고정(pin): 자주 보는 메모 상단 고정 (`notes.pinned bool` 1컬럼 추가,
    검색/정렬 결과와 무관하게 항상 최상단). ⚠️ `schema.sql` 대시보드 재실행
    필요.
  - **UX 다듬기(2026-08-06, 실사용 피드백 반영)**: 초기 이모지(📌/🔒/🔓)가
    너무 크고 눈에 띄어 흑백 SVG 아이콘(회색 톤, `PinIcon`/`LockIcon`)으로
    교체. 고정 아이콘은 고정된 메모에만 상시 노출, 고정 안 된 메모는 목록
    항목에 마우스를 올렸을 때만 나타남(항상 다 보이면 산만함). 비공개
    (`hide_preview`) 토글은 목록 행에서 편집기 상단(제목 입력 옆)으로
    이동 — 잠긴 메모가 아닌데도 자물쇠가 다 보여서 헷갈린다는 피드백,
    목록엔 이미 제목 아래 "🔒 비공개" 텍스트로 상태가 보이므로 별도 버튼은
    중복이라 판단. **진입 시 자동 선택 제거**: 낙서장 탭에 들어가자마자
    첫 메모 내용이 바로 보이는 게 프라이버시상 별로라는 피드백 — 이제 목록만
    보이고 메모를 클릭해야 내용이 열림(카카오톡 태블릿 버전과 유사한 느낌).
- **2단계 — 구조화**
  - 태그: `notes.tags text[]` + 태그 필터 (항목 참가자 태그 패턴 재사용)
  - 연결 메모 통합 뷰: 항목에 묶인 메모를 한곳에서 훑는 옵션 탭
- **3단계 — 표현력 (규모 큼, 나중)**
  - 리치 텍스트(3.1 참조)
  - 메모 간 링크, 이미지 첨부(Supabase Storage 필요)
- **추천 시작점**: 1단계(검색 + 정렬 + 고정). 가볍고 체감 효과 큼 — "쌓아두는 곳 → 찾아 쓰는 곳".

### 2.4 비공개성 · 되돌리기 · 자동저장 (2026-07-27 논의 시작)
현재 낙서장 목록은 제목+본문 미리보기가 그대로 노출되고(`NotesPage.tsx` 목록
버튼 안에 `n.body` 스니펫 표시), 저장은 수동 버튼/Ctrl+Cmd+S뿐이라 되돌리기가
없다. "실수로 본문을 지우고 그대로 저장돼버렸다"는 피드백에서 나온 후속 과제.

- **목록 미리보기 숨기기 — 완료(2026-07-27, 메모별 선택형으로 수정)**: 처음엔
  전체 메모의 미리보기를 일괄 제거했으나, "메모마다 선택하고 싶다"는 피드백으로
  범위 변경 — 기본은 기존처럼 본문 스니펫 노출, 메모별로 자물쇠 토글 버튼을
  눌러 숨기면(`notes.hide_preview bool`) 목록에 본문 대신 "🔒 비공개"만 표시.
  **주의**: 지금은 UI 표시만 가리는 것이고 서버측 암호화는 아니다(대시보드
  Table Editor나 다른 방법으로 열람 시 그대로 보임).
  - **향후 후보**: 숨긴 메모를 4자리 PIN으로 실제 암호화(지금 당장은 아님,
    2026-07-27 논의). 하려면 클라이언트 사이드 암호화(예: PIN에서 유도한 키로
    body를 암호화해 저장) 방식이 필요 — PIN을 서버에 평문으로 두면 의미가
    없고, PIN을 잊으면 복구 불가라는 트레이드오프도 미리 알려야 함.
    (2026-08-06: "비밀메모가 좀 더 실용적이었으면" 피드백 — 지금은 UI만
    가리는 수준이라 실제 암호화 없이는 "실용성"이 크게 안 느껴질 수 있음을
    시사. PIN 암호화 착수 시점을 앞당길지 재논의 필요.)
- **폴더 계층 — 결정(2026-07-27)**: 지금은 "폴더 없음" 또는 "1단계 폴더"만
  지원(하위 폴더 없음). 다만 나중에 트리로 확장할 여지를 남기기 위해 스키마는
  처음부터 트리 대응 형태로 만든다 — `note_folders`(id, owner_id, name,
  sort_order, `parent_id uuid null references note_folders(id)`) 테이블 +
  `notes.folder_id uuid null references note_folders(id)`. 지금 UI는
  `parent_id`를 항상 null로만 써서 평평한 목록만 노출하고, 트리 UI(하위 폴더
  펼치기 등)는 나중에 `parent_id`를 실제로 쓰기 시작하면 됨 — 이때도 추가
  마이그레이션이 필요 없다는 게 이 설계의 목적.
- **되돌리기 — 1순위 완료(2026-07-27)**: `ItemNote.tsx`에 "직전 자동저장 값"
  1단계 메모리 스냅샷(`undoBody` state) + 되돌리기 버튼 추가. 새 편집이
  시작될 때(`scheduleSave`)마다 그 직전 저장값을 기억해두고, 되돌리기를
  누르면 그 값으로 복원 후 즉시 저장(1단계라 한 번 쓰면 사라짐). 스키마
  변경 없음.
  - 낙서장에 자동저장을 추가할 때는 **자동저장만 먼저 넣지 않고** 같은
    스냅샷 되돌리기를 세트로 같이 넣는다.
  - "메모/연결메모 자체를 삭제" 하는 흐름(현재 `NotesPage.handleDelete`는
    `window.confirm` 확인창이 있음)에 대한 소프트 삭제(`deleted_at` +
    휴지통)는 더 낮은 우선순위 후속 과제로 유지.
- **자동저장 — 완료(2026-08-06)**: `ItemNote.tsx`의 debounce 저장 패턴(600ms)을
  `NotesPage.tsx`에도 그대로 적용, 메모 전환 시 대기 중이던 저장은 취소 대신
  즉시 flush(공유 타이머라 취소만 하면 방금 떠난 메모의 마지막 입력이 유실됨).
  - **되돌리기 버튼 — 결정(2026-08-06): 제거**. `NotesPage.tsx`로 옮기는
    과정에서 실제 버그 발견 — 저장 완료마다 `notes` 배열이 새 참조를 얻어
    `selected` 객체도 매번 바뀌는데, 이걸 의존성으로 쓰는 `useEffect`가
    되돌리기 스냅샷/상태 텍스트를 거의 즉시 초기화해버려 사실상 안 뜬다.
    고치기 전에 "애초에 이 버튼이 필요한가"를 사용자에게 재확인한 결과,
    브라우저 네이티브 Ctrl+Z가 겹치는 영역(방금 타이핑한 것 취소)은 이미
    충분히 커버하고 이 버튼이 값어치를 하는 건 "메모 전환 후 복귀"처럼 좁은
    경우뿐이라 제거하기로 함(제대로 고치려면 다단계 되돌리기/히스토리 유지로
    스코프가 커짐). `ItemNote.tsx`의 되돌리기는 이 버그 영향 없어 그대로 유지
    (그쪽은 `itemId`가 바뀔 때만 리셋하는 별도 effect라 저장 완료로 트리거
    안 됨).
  - **저장 버튼 제거 후 레이아웃 — 결정(2026-08-06): 보류 유지**. 편집기
    하단 액션 줄에 "삭제"만 남아 붕 뜬 느낌은 인지하고 있으나 당장은 그대로
    두기로 함. 필요해지면 재검토.
- **오래된 메모 보관(archive) — 제안(2026-08-06)**: "확인 안 하는 예전 메모를
  안 보이게 옮겨두기" 요청. 폴더(위 결정)와 겹치는 부분이 있어 폴더 구현
  시점에 "보관함" 성격의 폴더 하나로 흡수할지, 별도 `notes.archived bool`
  컬럼으로 분리할지 같이 결정하는 게 좋아 보임. 고정(pin, 2장 1단계)과
  반대 극의 기능이라 목록 UI 설계(고정 상단 / 기본 / 보관 숨김) 한 번에
  같이 보는 게 나을 듯. 착수 전 결정 필요.

## 3. 보류된 기능

### 3.1 메모 서식 (리치 텍스트)
- **현재**: 기본 저장 단축키(Ctrl/Cmd+S)만. 텍스트 서식 없음.
- **방향**: TipTap 헤드리스 에디터.
  - 굵게 / 기울임 / 밑줄 / 취소선, 글자색 4~5 프리셋, 크기 3단계, 불릿·체크리스트
  - `notes.body`를 HTML로 저장 → 기존 평문 메모는 그대로 텍스트로 표시(하위호환)
  - CSV 내보내기는 항목 content만 쓰므로 영향 없음
- **트레이드오프**: 의존성 1개 추가. 낙서장·연결 메모 양쪽에 영향.
- **대안 후보(2026-08-06 제안)**: 마크다운 문법 그대로 저장 + 렌더링(WYSIWYG
  아닌 텍스트 편집 + 미리보기/렌더 전환). TipTap보다 가볍고 의존성도 작지만
  "타이핑하며 바로 보이는" 경험은 약함. 노션처럼 무거워지는 걸 원치 않으면
  이쪽이 더 낙서장 성격에 맞을 수 있음 — 방향 결정은 보류.

### 3.2 좁은 AI (Edge Function)
- 자연어로 항목 추가(예: "내일 3시 팀미팅"), 주간 회고 요약 등 경계가 뚜렷한 기능.
- API 키 보호 위해 Supabase Edge Function 필요(프론트에 키 금지) → 백엔드 첫 도입 명분.
- 지금 데이터가 구조화(시간·참가자·서브태스크)돼 있어 나중에 붙이기 쉬움. 당장은 안 함.

## 4. 운영/유지보수 메모

### 4.1 공휴일 데이터 갱신
- `src/lib/holidays.ts` 정적 데이터셋. **2024~2027**은 음력(설날·추석·부처님오신날)·대체공휴일 포함, **2028~2030**은 양력 고정공휴일만.
- 음력·대체공휴일은 매년 바뀌므로 관보/공공데이터포털 확인해 연도별로 추가·보정 필요.
- 대안(향후): 공공데이터 API + 캐시, 또는 음력 계산 라이브러리.
- **버그 발견·수정(2026-08-06)**: 사용자가 "이번 대체공휴일이 안 보인다"고
  보고 — 확인해보니 2026년 광복절(8/15, 토)·개천절(10/3, 토) 대체공휴일
  (각각 8/17, 10/5)이 데이터셋에 통째로 빠져 있었음(렌더링 버그 아니라
  데이터 누락). 같은 방식으로 다른 연도도 전수 재검산한 결과 2027년
  한글날(10/9, 토)·크리스마스(12/25, 토) 대체공휴일(10/11, 12/27)도 누락
  발견해 함께 추가. 추가로 2027년에 **잘못** 들어있던 `2027-06-07`(현충일
  대체)도 발견해 제거 — 현충일은 국경일이 아니라 대체공휴일 대상 자체가
  아님(신정도 마찬가지로 제외). 대체공휴일 대상: 설날·추석 연휴, 어린이날,
  국경일 4개(3.1/8.15/10.3/10.9), 부처님오신날, 크리스마스.

### 4.2 스키마 마이그레이션 적용 대기
- `items.accent`(중요도 색) 컬럼 — Supabase SQL Editor에서 실행해야 저장됨:
  `alter table items add column if not exists accent text;`
- 원칙: 스키마 변경 시 `supabase/schema.sql`에 idempotent 구문으로 추가하고 대시보드에서 재실행.

### 4.3 대량 데이터 페이지네이션
- `listAllItems`(CSV) / `listNotes`는 전체 조회 → 데이터 누적 시 PostgREST 기본 반환 행 제한에 걸릴 수 있음.
- 향후 range 헤더 기반 페이지네이션 보강.

## 5. 아키텍처/방향성 논의 요약 (참고)

- **보안**: 사용자 간에는 RLS로 격리되지만, 프로젝트 소유자(운영자)는 평문 DB 열람 가능.
  "운영자도 못 봄" 수준이 필요하면 클라이언트측 E2E 암호화가 별도 과제(검색·가공 포기 트레이드오프 큼).
- **정체성/차별점**: 시간 슬롯 중심의 구글/기본 캘린더와 달리 **카테고리×날짜 매트릭스**가 핵심.
  정면 경쟁(알림·초대·회의)보다 매트릭스 + 심층 할일 + 메모 결합으로 차별. 구글 캘린더는
  "동기화" 대신 "읽어와 겹쳐 보기(오버레이)"가 승산 있음.
- **앱/위젯**: PWA(가장 쌈) → Capacitor(웹 재활용 앱) → 네이티브 위젯(가장 비쌈) 순.
  현재 Supabase API 중심 구조는 나중에 위젯이 데이터를 가져오기에 유리.
