## 1. 미해결 결정 (논의 중)

### 1.1 시간 입력 단위 — 1분 vs 5분
- **현재 상태**: 1분 단위 (시/분 드롭다운, 분 00~59).
- **고민**:
  - 1분: 정밀하지만 분 드롭다운 옵션이 60개라 길다.
  - 5분: 빠르고 짧지만 `14:37` 같은 값은 못 넣는다.
- **후보 대안**:
  - (a) 분을 텍스트로 직접 입력 허용 + 검증
  - (b) 5분 기본 + "직접 입력" 토글로 미세조정
  - (c) 자주 쓰는 프리셋(00/30) 빠른 버튼 + 드롭다운 병행
- **결정**: 보류. 실제 사용 패턴 보고 결정.

### 1.2 피드백 확인 방법 — 관리자 계정 vs 대안 (2026-07-27 논의 시작)
- **현재 상태**: `feedback` 테이블 select/insert 정책이 `auth.uid() = owner_id`뿐이라,
  본인이 남긴 피드백만 본인 계정으로 조회 가능. 운영자(개발자)가 다른 사용자의
  피드백을 앱 안에서 볼 방법이 없음.
- **후보**:
  - (a) **당장·무료**: Supabase 대시보드 Table Editor에서 `feedback` 테이블을
    직접 확인 (대시보드는 RLS를 우회하는 관리 세션이라 전체 행이 보임). 코드
    변경 0, 지금 바로 가능.
  - (b) **가벼운 앱 내 조회(추천)**: `feedback` select 정책에 본인 UID 예외를
    추가(`auth.uid() = owner_id or auth.uid() = '<내 UID>'`) + 설정 탭에 본인
    UID일 때만 보이는 "피드백 보기" 섹션 추가. 새 역할/테이블 없이 정책 1줄 +
    작은 목록 컴포넌트로 해결.
  - (c) **역할 테이블**(`admin_users` 등)로 정식 관리자 개념 도입 — 지금
    규모엔 과함, 비추천.
  - (d) **알림형**(피드백 insert 시 이메일/슬랙으로 통지) — Database Webhook +
    Edge Function 필요(서버 코드 최초 도입 명분). 지금 단계엔 오버킬.
- **결정**: 보류. (b)를 1순위로 검토 예정.

## 2. 낙서장 발전 로드맵

현재 낙서장 = 목록 + 제목/본문 편집 + 저장/삭제 (최소 형태). 단계적으로 확장.

- **1단계 — 탐색·정리 (저비용, 즉효)**
  - 검색: 제목·본문 키워드 필터 (클라이언트 필터, 서버 변경 없음)
  - 정렬 옵션: 최근 수정순 / 제목순 토글
  - 고정(pin): 자주 보는 메모 상단 고정 (`notes.pinned bool` 1컬럼 추가)
- **2단계 — 구조화**
  - 태그: `notes.tags text[]` + 태그 필터 (항목 참가자 태그 패턴 재사용)
  - 연결 메모 통합 뷰: 항목에 묶인 메모를 한곳에서 훑는 옵션 탭
- **3단계 — 표현력 (규모 큼, 나중)**
  - 리치 텍스트(3.1 참조)
  - 메모 간 링크, 이미지 첨부(Supabase Storage 필요)
- **추천 시작점**: 1단계(검색 + 정렬 + 고정). 가볍고 체감 효과 큼 — "쌓아두는 곳 → 찾아 쓰는 곳".

### 2.4 비공개성 · 되돌리기 · 자동저장 (2026-07-27 논의 시작)
현재 낙서장 목록은 제목+본문 미리보기가 그대로 노출되고(`NotesPage.tsx` 목록
버튼 안에 `n.body` 스니펫 표시), 저장은 수동 버튼/Ctrl+Cmd+S뿐이라 되돌리기가
없다. "실수로 본문을 지우고 그대로 저장돼버렸다"는 피드백에서 나온 후속 과제.

- **목록 미리보기 숨기기**: 본문 스니펫을 목록에서 빼고 제목만(또는 "제목 없음"
  일 때는 그것도 흐리게) 노출 — 스키마 변경 없이 `NotesPage.tsx` 렌더 부분만
  수정하면 됨. 저비용·즉효.
- **폴더 계층 — 결정(2026-07-27)**: 지금은 "폴더 없음" 또는 "1단계 폴더"만
  지원(하위 폴더 없음). 다만 나중에 트리로 확장할 여지를 남기기 위해 스키마는
  처음부터 트리 대응 형태로 만든다 — `note_folders`(id, owner_id, name,
  sort_order, `parent_id uuid null references note_folders(id)`) 테이블 +
  `notes.folder_id uuid null references note_folders(id)`. 지금 UI는
  `parent_id`를 항상 null로만 써서 평평한 목록만 노출하고, 트리 UI(하위 폴더
  펼치기 등)는 나중에 `parent_id`를 실제로 쓰기 시작하면 됨 — 이때도 추가
  마이그레이션이 필요 없다는 게 이 설계의 목적.
- **되돌리기 — 결정(2026-07-27)**: 진짜 문제 지점은 낙서장(`NotesPage.tsx`,
  수동 저장/Ctrl+S)이 아니라 **항목 연결 메모(`ItemNote.tsx`)** 다. 이미
  자동저장(600ms 디바운스)이라 되돌릴 틈이 없고, 패널을 닫고 다시 열면
  브라우저 네이티브 Ctrl+Z 히스토리도 리마운트로 날아간다(낙서장은 아직
  자동저장이 없어 저장 전까지는 네이티브 Ctrl+Z가 먹힘 — "상황에 따라
  된다"던 게 이 차이). 범위:
  - 1순위: `ItemNote.tsx`에 "마지막 자동저장 직전 값" 1단계 메모리 스냅샷 +
    되돌리기 버튼(스키마 변경 없음, 최저비용).
  - 낙서장에 자동저장을 추가할 때는 **자동저장만 먼저 넣지 않고** 같은
    스냅샷 되돌리기를 세트로 같이 넣는다.
  - "메모/연결메모 자체를 삭제" 하는 흐름(현재 `NotesPage.handleDelete`는
    `window.confirm` 확인창이 있음)에 대한 소프트 삭제(`deleted_at` +
    휴지통)는 더 낮은 우선순위 후속 과제로 유지.
- **자동저장**: `ItemNote.tsx`의 debounce 저장 패턴(600ms)을 `NotesPage.tsx`에도
  그대로 적용. 위 "되돌리기 1순위" 작업과 같은 배치로 진행.

## 3. 보류된 기능

### 3.1 메모 서식 (리치 텍스트)
- **현재**: 기본 저장 단축키(Ctrl/Cmd+S)만. 텍스트 서식 없음.
- **방향**: TipTap 헤드리스 에디터.
  - 굵게 / 기울임 / 밑줄 / 취소선, 글자색 4~5 프리셋, 크기 3단계, 불릿·체크리스트
  - `notes.body`를 HTML로 저장 → 기존 평문 메모는 그대로 텍스트로 표시(하위호환)
  - CSV 내보내기는 항목 content만 쓰므로 영향 없음
- **트레이드오프**: 의존성 1개 추가. 낙서장·연결 메모 양쪽에 영향.

### 3.2 좁은 AI (Edge Function)
- 자연어로 항목 추가(예: "내일 3시 팀미팅"), 주간 회고 요약 등 경계가 뚜렷한 기능.
- API 키 보호 위해 Supabase Edge Function 필요(프론트에 키 금지) → 백엔드 첫 도입 명분.
- 지금 데이터가 구조화(시간·참가자·서브태스크)돼 있어 나중에 붙이기 쉬움. 당장은 안 함.

## 4. 운영/유지보수 메모

### 4.1 공휴일 데이터 갱신
- `src/lib/holidays.ts` 정적 데이터셋. **2024~2027**은 음력(설날·추석·부처님오신날)·대체공휴일 포함, **2028~2030**은 양력 고정공휴일만.
- 음력·대체공휴일은 매년 바뀌므로 관보/공공데이터포털 확인해 연도별로 추가·보정 필요.
- 대안(향후): 공공데이터 API + 캐시, 또는 음력 계산 라이브러리.

### 4.2 스키마 마이그레이션 적용 대기
- `items.accent`(중요도 색) 컬럼 — Supabase SQL Editor에서 실행해야 저장됨:
  `alter table items add column if not exists accent text;`
- 원칙: 스키마 변경 시 `supabase/schema.sql`에 idempotent 구문으로 추가하고 대시보드에서 재실행.

### 4.3 대량 데이터 페이지네이션
- `listAllItems`(CSV) / `listNotes`는 전체 조회 → 데이터 누적 시 PostgREST 기본 반환 행 제한에 걸릴 수 있음.
- 향후 range 헤더 기반 페이지네이션 보강.

## 5. 아키텍처/방향성 논의 요약 (참고)

- **보안**: 사용자 간에는 RLS로 격리되지만, 프로젝트 소유자(운영자)는 평문 DB 열람 가능.
  "운영자도 못 봄" 수준이 필요하면 클라이언트측 E2E 암호화가 별도 과제(검색·가공 포기 트레이드오프 큼).
- **정체성/차별점**: 시간 슬롯 중심의 구글/기본 캘린더와 달리 **카테고리×날짜 매트릭스**가 핵심.
  정면 경쟁(알림·초대·회의)보다 매트릭스 + 심층 할일 + 메모 결합으로 차별. 구글 캘린더는
  "동기화" 대신 "읽어와 겹쳐 보기(오버레이)"가 승산 있음.
- **앱/위젯**: PWA(가장 쌈) → Capacitor(웹 재활용 앱) → 네이티브 위젯(가장 비쌈) 순.
  현재 Supabase API 중심 구조는 나중에 위젯이 데이터를 가져오기에 유리.

## 7. 향후 업데이트 후보 (효과 대비 난이도별)

### A. 바로 할 만한 것 (저비용·체감 큼)
- 전체 검색: 항목·메모 키워드 검색
- 낙서장 검색/정렬/고정 (2장 1단계)
- 완료 숨기기 / 필터 (완료·참가자·중요도별)
- 이전 주 복제 (반복 주간계획 한 번에 복사)
- 다크 모드 (설정 토글, Tailwind `dark:`)
- 주 시작 요일 설정 (현재 월요일 고정 → 일요일 선택)
- 시간 입력 단위 확정 (1분/5분 — 1.1 논의 중)

### B. 플래너 기능 강화 (중간)
- 드래그 이동/재정렬 (셀 간 이동·셀 내 순서, fractional index)
- 반복 항목 (매주/매일 규칙)
- 마감일·D-day (기한 + 임박 강조) — **구현 완료(2026-07-27, 코드 기준)**: 별도
  목표일 컬럼 없이 항목이 놓인 셀의 `date`를 D-day 기준일로 재사용.
  `items.show_dday bool default false` 컬럼, 상세 패널 토글, 매트릭스 셀
  `D-N`/`D-day`/`D+N` 배지. ⚠️ `schema.sql` 대시보드 재실행 전까지는 저장 안 됨.
- 주간 대시보드 (카테고리별 완료율·진행 통계)
- 아젠다/타임라인 뷰 (start_time 기반 시간순 리스트)
- CSV 가져오기 / iCal 내보내기
- 메모 리치 텍스트 (TipTap — 3.1)

### C. 플랫폼·동기화 (중상)
- PWA (설치형 + 오프라인) — 비용 대비 효과 최고
- 실시간 동기화 (Supabase Realtime, 다기기 동시 사용)
- 모바일 앱 (Capacitor)
- 홈 위젯 (네이티브 필요, 가장 비쌈)

### D. 큰 방향 (미래·규모 큼)
- 좁은 AI (Edge Function): 자연어 항목 추가, 주간 회고 요약 (3.2)
- 구글 캘린더 오버레이 (동기화 아닌 읽어와 겹쳐 보기)
- 공유/협업 (읽기전용 링크 → 팀 편집, RLS 확장)
- E2E 암호화 (운영자도 못 봄, 검색·가공 트레이드오프)
- 첨부파일/이미지 (Supabase Storage)

### E. 품질·기반 (안 보이지만 중요)
- 대량 데이터 페이지네이션 (CSV/메모 전체 조회 한계 대비 — 4.3)
- 접근성 (키보드 내비게이션, 스크린리더)
- 에러 모니터링 (Sentry 등)
- 다국어(i18n)
