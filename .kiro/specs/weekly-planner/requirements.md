# 요구사항 (Requirements)

## 개요

기존에 엑셀 공유 파일로 관리하던 개인 일정을 웹앱으로 옮긴다. 일반 캘린더처럼
"날짜 = 칸 하나"가 아니라 **카테고리(행) × 날짜(열)** 2차원 격자로 일정을 관리하는 것이
이 프로젝트의 핵심 정체성이다. 여러 기기에서 같은 데이터에 접근할 수 있도록 로그인과
클라우드 저장(Supabase)을 사용한다.

### 범위 밖 (이번 버전에서 하지 않음)
- 팀/공유 기능 (단, 데이터 구조는 `owner_id` 기반으로 확장 가능하게 유지)
- 오프라인 편집 및 충돌 해결
- 실시간 동기화(Supabase Realtime) — 페이지 진입 시 fetch로 충분
- 항목 셀 간 드래그 이동/재정렬 (카테고리 순서변경은 포함)

### 용어 정의
- **카테고리(category)**: 매트릭스의 행. 예: 마감, 일정, 공부.
- **항목(item)**: 하나의 (카테고리, 날짜) 셀 안에 들어가는 한 줄의 할 일/메모.
- **셀(cell)**: (카테고리, 날짜) 조합. 0개 이상의 항목을 세로로 나열.
- **주(week)**: 월요일 시작 7일. 매트릭스의 기본 단위이자, 월간 달력에서는 한 행(가로 줄).
- **주간 뷰**: 카테고리(행) × 그 주 7일(열) 매트릭스. 셀마다 항목을 세로로 나열하는 **상세 뷰**.
- **월간 뷰**: 주(월~일)를 세로로 쌓은 **평범한 달력 그리드**(개요 뷰). 각 날짜 칸에 그날의 항목을 카테고리 색으로 요약.
- **하루 경계 시각(day rollover)**: "오늘"이 다음 날로 넘어가는 기준 시각. 사용자가 설정(예: 04:00). 백준의 "하루 시작 시각" 개념과 동일.
- **낙서장(note)**: 매트릭스와 분리된 자유 형식 메모.

## 요구사항 1 — 인증 (이메일 / 구글 로그인)

**사용자 스토리:** 사용자로서, 여러 기기에서 같은 일정 데이터에 접근하기 위해
이메일 또는 구글 계정으로 로그인하고 싶다.

### 수용 기준
1. WHEN 로그인하지 않은 사용자가 앱에 접근하면 THEN 시스템은 로그인 화면을 표시해야 한다(SHALL).
2. WHEN 사용자가 이메일/비밀번호 또는 구글 계정으로 로그인하면 THEN 시스템은 해당 사용자의 세션을 생성하고 매트릭스 화면으로 이동해야 한다.
3. WHEN 인증된 사용자가 앱을 다시 열면 THEN 시스템은 기존 세션을 복원하여 재로그인 없이 데이터를 표시해야 한다.
4. WHEN 사용자가 로그아웃하면 THEN 시스템은 세션을 종료하고 로그인 화면으로 이동해야 한다.
5. 시스템은 각 사용자가 자신의 `owner_id`에 해당하는 데이터에만 접근하도록 보장해야 한다(RLS로 강제).

## 요구사항 2 — 주간 매트릭스 뷰

**사용자 스토리:** 사용자로서, 카테고리를 행으로, 그 주의 날짜 7개를 열로 하는
2차원 격자에서 한 주의 일정을 한눈에 보고 싶다.

### 수용 기준
1. WHEN 사용자가 매트릭스 화면에 진입하면 THEN 시스템은 세로축에 사용자의 카테고리들을(정렬 순서대로), 가로축에 현재 주의 날짜 7개를 배치한 격자를 표시해야 한다.
2. WHEN 특정 (카테고리, 날짜) 셀에 항목이 여러 개 있으면 THEN 시스템은 그 항목들을 셀 안에 세로로 나열해야 한다.
3. 시스템은 각 열 머리글에 날짜와 요일을 표시해야 하며, "오늘"(하루 경계 시각으로 판정한 논리적 오늘, 요구사항 9)에 해당하는 열을 시각적으로 구분해야 한다.
4. WHEN 항목이 없는 셀이면 THEN 시스템은 클릭 가능한 빈 셀을 표시해야 한다.
5. WHEN 카테고리가 하나도 없으면 THEN 시스템은 카테고리를 먼저 추가하도록 안내해야 한다.

---

## 요구사항 3 — 항목 CRUD

**사용자 스토리:** 사용자로서, 각 셀에 할 일/메모 항목을 자유롭게 추가·수정·삭제하고 싶다.

### 수용 기준
1. WHEN 사용자가 셀(빈 영역 또는 "추가" 액션)을 클릭하면 THEN 시스템은 해당 (카테고리, 날짜)에 새 항목을 입력할 수 있는 UI를 제공해야 한다.
2. WHEN 사용자가 내용을 입력하고 저장하면 THEN 시스템은 항목을 저장하고 해당 셀 하단에 즉시 표시해야 한다.
3. WHEN 사용자가 기존 항목을 클릭하면 THEN 시스템은 편집/삭제할 수 있는 UI를 제공해야 한다.
4. WHEN 사용자가 항목을 수정하고 저장하면 THEN 시스템은 변경 내용을 저장하고 `updated_at`을 갱신해야 한다.
5. WHEN 사용자가 항목을 삭제하면 THEN 시스템은 해당 항목을 저장소에서 제거하고 화면에서 없애야 한다.
6. 시스템은 같은 셀 안 항목들을 안정적인 순서(정렬 순서 → 생성 시각)로 표시해야 한다.
7. (선택) 시스템은 항목의 완료(done) 상태를 토글할 수 있어야 하며, 완료 항목을 시각적으로 구분해야 한다.

---

## 요구사항 4 — 주 단위 이동

**사용자 스토리:** 사용자로서, 이전/다음 주로 이동하며 다른 주의 일정을 보고 싶다.

### 수용 기준
1. 시스템은 상단에 현재 주 표시(예: "7월 3주차")와 이전/다음 이동 버튼을 제공해야 한다.
2. WHEN 사용자가 "다음"/"이전" 버튼을 누르면 THEN 시스템은 표시 기준일을 ±7일(주간) 또는 ±1개월(월간) 이동하고 해당 범위의 데이터를 다시 조회해야 한다.
3. 시스템은 "오늘"로 즉시 돌아가는 수단(예: "이번 주" 버튼)을 제공해야 한다.
4. WHEN 주가 바뀌면 THEN 시스템은 그 범위에 해당하는 항목만 표시해야 한다(다른 주의 항목은 보이지 않음).

---

## 요구사항 5 — 카테고리 관리 (추가/삭제/순서변경)

**사용자 스토리:** 사용자로서, 내 관리 방식에 맞게 카테고리(행)를 추가·삭제하고
순서를 바꾸고 싶다.

### 수용 기준
1. WHEN 사용자가 카테고리를 추가하면 THEN 시스템은 이름(및 색상)을 받아 새 행으로 매트릭스에 추가해야 한다.
2. WHEN 사용자가 카테고리를 삭제하면 THEN 시스템은 확인을 받은 뒤 해당 카테고리와 그에 속한 모든 항목을 함께 삭제해야 한다.
3. WHEN 사용자가 카테고리 순서를 변경하면 THEN 시스템은 변경된 정렬 순서를 저장하고, 이후 매트릭스에서 그 순서대로 행을 표시해야 한다.
4. WHEN 카테고리 삭제로 항목이 함께 사라지는 경우 THEN 시스템은 삭제 전에 사용자에게 명시적으로 경고해야 한다.

---

## 요구사항 6 — 주간/월간 뷰 토글

**사용자 스토리:** 사용자로서, 상세하게 볼 때는 카테고리 매트릭스(주간)로, 한 달을
멀리서 훑을 때는 평범한 달력(월간)으로 전환하고 싶다. (토스의 주별/월별 소비 화면처럼
같은 데이터를 "상세 ↔ 개요"로 전환한다.)

### 수용 기준
1. 시스템은 주간/월간 전환 토글을 제공해야 한다.
2. WHEN 사용자가 주간을 선택하면 THEN 시스템은 카테고리(행) × 그 주 7일(열) 매트릭스(상세 뷰)를 표시해야 한다.
3. WHEN 사용자가 월간을 선택하면 THEN 시스템은 **평범한 달력 그리드**(주=행, 요일=열, 월요일 시작, 5~6행)를 표시해야 하며, 가로로 늘어나서는 안 된다.
4. WHEN 월간 달력의 한 날짜 칸에 항목이 있으면 THEN 시스템은 그 날의 항목들을 카테고리 색으로 구분해 요약 표시해야 하며, 칸이 넘치면 "+N" 형태로 축약해야 한다.
5. WHEN 사용자가 월간 달력에서 특정 날짜(또는 주)를 선택하면 THEN 시스템은 해당 주의 주간 매트릭스로 전환(드릴다운)해야 한다.
6. 시스템은 월간 달력에서 현재 달에 속하지 않는 앞뒤 날짜 칸을 시각적으로 흐리게 구분해야 한다.
7. 주간·월간 두 뷰는 표현만 다를 뿐 동일한 (카테고리, 날짜, 항목) 데이터를 사용해야 한다(조회 날짜 범위와 렌더링 방식만 달라진다).

## 요구사항 7 — 낙서장 (자유 형식 메모)

**사용자 스토리:** 사용자로서, 매트릭스와 분리된 별도 페이지에서 자유롭게 메모하고 싶다.

### 수용 기준
1. 시스템은 매트릭스와 분리된 낙서장 페이지로 이동할 수단을 제공해야 한다.
2. 시스템은 메모의 생성·조회·수정·삭제를 지원해야 한다.
3. WHEN 사용자가 메모 내용을 편집하고 저장하면 THEN 시스템은 내용을 저장하고 `updated_at`을 갱신해야 한다.
4. 낙서장 데이터는 매트릭스 데이터와 독립적이어야 한다(한쪽 변경이 다른 쪽에 영향을 주지 않음).

---

## 요구사항 8 — CSV 내보내기

**사용자 스토리:** 사용자로서, 서비스를 그만 쓰더라도 데이터를 보존하고 엑셀로
되돌릴 수 있도록 CSV로 내보내고 싶다.

### 수용 기준
1. WHEN 사용자가 "CSV 내보내기"를 실행하면 THEN 시스템은 사용자의 항목 데이터를 CSV 파일로 생성하여 다운로드해야 한다.
2. CSV는 최소한 카테고리 이름, 날짜, 내용, 완료 여부 열을 포함해야 한다.
3. 시스템은 한글이 엑셀에서 깨지지 않도록 UTF-8(BOM 포함) 인코딩으로 파일을 생성해야 한다.
4. 내보내기는 별도 서버 없이 클라이언트에서 수행되어야 한다.

---

## 요구사항 9 — 사용자 설정 (하루 경계 시각)

**사용자 스토리:** 사용자로서, 늦게까지 활동하는 생활 패턴에 맞춰 "하루가 넘어가는 시각"을
직접 정하고 싶다. (백준의 "하루 시작 시각" 설정이 레퍼런스 — 예: 새벽 4시로 두면
새벽 2시에 접속해도 아직 '어제'로 취급된다.)

### 수용 기준
1. 시스템은 하루 경계 시각(0~23시)을 설정하는 UI를 제공해야 하며, 기본값은 0시(자정)여야 한다.
2. WHEN 하루 경계 시각이 H로 설정되어 있으면 THEN 시스템은 "논리적 오늘"을 `(현재시각 - H시간)의 날짜`로 계산해야 한다.
3. 시스템은 이 논리적 오늘을 기준으로 (a) 진입 시 표시할 주/달, (b) "오늘" 열 하이라이트, (c) 항목 추가 시 기본 날짜를 결정해야 한다.
4. 하루 경계 시각은 이미 **저장된 항목의 날짜 값을 바꾸지 않는다**(항목 날짜는 사용자가 지정한 값 그대로 유지). 이 설정은 "오늘"의 판정과 기본값 계산에만 영향을 준다.
5. WHEN 사용자가 설정을 변경하면 THEN 시스템은 값을 DB에 저장하여 다른 기기에서도 동일하게 적용되도록 해야 한다.

## 비기능 요구사항 (보안·기술 제약)

1. **RLS 필수:** 모든 테이블에 `owner_id`(auth.users 참조)를 두고 RLS를 활성화한다. 사용자는 자신의 `owner_id` 행만 select/insert/update/delete 할 수 있어야 한다.
2. **키 관리:** 프론트엔드는 Supabase anon key만 사용한다. service_role key는 프론트엔드 코드/저장소에 절대 포함하지 않는다.
3. **환경변수:** `.env`는 `.gitignore`에 포함한다. `VITE_` 접두사 값은 브라우저에 노출됨을 전제로 다룬다.
4. **BaaS:** 별도 서버 코드를 작성하지 않는다(Supabase만 사용).
5. **상태관리:** 별도 상태관리 라이브러리를 도입하지 않고 React 기본 상태로 시작한다.
6. **확장성:** 지금은 개인용이지만, 팀/공유로 확장 가능한 데이터 구조를 유지한다(단, 공유 기능 자체는 구현하지 않는다).
7. **설정 동기화:** 사용자 설정(하루 경계 시각 등)은 로컬이 아닌 DB에 저장하여 여러 기기에서 동일하게 적용한다.
8. **주 시작 요일:** 월요일 고정(상수). 지금은 설정으로 노출하지 않는다(필요 시 설정 테이블에 추가 가능).
9. **UI 품질:** 주간 매트릭스를 주인공으로 하는 깔끔하고 정돈된 화면을 지향한다. 넉넉한 여백, 명확한 정보 위계, 절제된 색 사용을 따른다(구체 가이드는 design.md 8장). 별도 UI 컴포넌트 라이브러리는 도입하지 않고 Tailwind로 구현한다.
10. **뷰 관계:** 기본 진입은 주간 뷰이며 일정·할일 관리는 주간에서 수행한다. 월간은 개요용 전환 뷰로, 관리 동작은 주간으로 드릴다운해 처리한다.

# 확장 요구사항 (v2) — 종합 다이어리로의 진화

v1(요구사항 1~9)은 구현 완료됐다. v2는 "캘린더 + 할일 + 플래너 + 다이어리"를 한 화면
위계로 묶는 방향으로 확장한다. 설계 철학은 **노션의 재발명을 피하고 최소 필드만 1급으로,
나머지는 연결된 메모로** 흡수한다.

### v2 범위 밖 (의도적으로 하지 않음)
- **AI 비서**: 이번 범위 밖. 단, 데이터를 구조화(시간·참가자·서브태스크)해 두어 향후
  Supabase Edge Function 기반의 **좁은 AI 기능**(자연어로 항목 추가, 주간 회고 요약)을
  붙이기 쉽게만 준비한다. (API 키 보호를 위해 서버측 함수가 필요하므로 백엔드 도입 시점의 명분)
- **실시간 협업/공유/초대**: 참가자는 "이름 태그"일 뿐 계정·권한·알림이 아니다.
- **스케줄링 엔진**: 시간은 "라벨 + 정렬"용이며 알림·충돌검사·타임라인은 하지 않는다.

### 용어 추가
- **항목 상세(item detail)**: 한 항목을 펼쳤을 때 보이는 패널. 내용·완료·시간·참가자·
  서브태스크·연결 메모를 한곳에서 다룬다.
- **서브태스크(subtask)**: 한 항목에 종속된 세부 체크리스트 한 줄.
- **연결 메모(item note)**: 특정 항목에 1:1로 묶인 메모. 낙서장 전역 목록엔 기본 노출 안 함.
- **독립 메모**: 기존 낙서장 메모(어떤 항목에도 묶이지 않음).

## 요구사항 10 — 항목 상세 뷰

**사용자 스토리:** 사용자로서, 한 줄 할일을 클릭해 펼치면 그와 관련된 세부 정보를
한곳에서 보고 편집하고 싶다.

### 수용 기준
1. WHEN 사용자가 항목을 클릭(확장)하면 THEN 시스템은 항목 상세 패널을 표시해야 한다.
2. 상세 패널에서 사용자는 내용, 완료 상태, 시작 시각(선택), 참가자 태그(선택),
   서브태스크 체크리스트, 연결 메모에 접근·편집할 수 있어야 한다.
3. 상세에서의 변경은 낙관적으로 즉시 반영되고 실패 시 롤백·토스트로 처리해야 한다(v1 3.10 정책 계승).

---

## 요구사항 11 — 서브태스크(세부 체크리스트)

**사용자 스토리:** 사용자로서, 하나의 할일 아래에 세부 단계를 체크리스트로 관리하고 싶다.

### 수용 기준
1. 시스템은 항목 상세에서 서브태스크의 추가·수정·삭제·순서 유지·완료 토글을 지원해야 한다.
2. 시스템은 상위 항목에 서브태스크 진행률(예: 2/5)을 요약 표시해야 한다.
3. 서브태스크는 상위 항목 삭제 시 함께 삭제되어야 한다(cascade).

---

## 요구사항 12 — 시간 정보 및 정렬

**사용자 스토리:** 사용자로서, 할일에 시간을 적어두면 그 시간 순서대로 정렬되어
하루의 흐름을 파악하고 싶다.

### 수용 기준
1. 시스템은 항목에 선택적 시작 시각(HH:MM)을 입력받아야 한다(시간 없는 항목도 허용).
2. WHEN 한 셀(또는 월간의 한 날짜)에 여러 항목이 있으면 THEN 시스템은
   **시간이 있는 항목을 시각 오름차순으로 먼저**, 시간이 없는 항목을 그 뒤에 정렬 순서대로
   표시해야 한다.
3. 주간 매트릭스 셀과 월간 요약 모두 동일한 정렬 규칙을 따라야 한다.
4. 시간은 표시·정렬 목적이며, 알림/충돌검사/타임라인 뷰는 제공하지 않는다.

---

## 요구사항 13 — 참가자 태그

**사용자 스토리:** 사용자로서, 이 일을 누구와/어느 조직에서 하는지 이름 태그로 표시하고 싶다.

### 수용 기준
1. 시스템은 항목에 0개 이상의 자유 텍스트 참가자 태그를 입력받아야 한다.
2. 시스템은 태그를 항목 상세(및 가능하면 셀)에 칩 형태로 표시해야 한다.
3. 참가자 태그는 단순 라벨이며 계정·초대·공유·알림을 수반하지 않는다.

---

## 요구사항 14 — 항목 연결 메모

**사용자 스토리:** 사용자로서, 할일을 펼쳐 그 할일 전용 메모장에 자세한 내용을 적고 싶다.

### 수용 기준
1. 시스템은 각 항목에 1:1로 연결되는 메모를 가질 수 있게 해야 한다.
2. WHEN 사용자가 항목 상세에서 "메모 열기/작성"을 시작하면 THEN 시스템은 그때 연결 메모를
   생성해야 한다(펼치기만으로 빈 메모를 자동 양산하지 않는다).
3. 연결 메모는 낙서장 전역 목록에 기본 노출되지 않으며, 항목 상세를 통해 접근한다.
4. 메모 편집기에서 사용자는 간단한 동작으로 체크리스트를 삽입할 수 있어야 한다(경량 지원).
5. 연결 메모는 상위 항목 삭제 시 함께 삭제되어야 한다(cascade).

---

## 요구사항 15 — 카테고리를 설정 계층으로

**사용자 스토리:** 사용자로서, 카테고리는 자주 바꾸는 게 아니라 초기 세팅·간헐 조정
대상이므로, 상시 메뉴가 아니라 설정 안에서 관리하고 싶다.

### 수용 기준
1. 시스템은 카테고리 관리 UI를 상단 상시 메뉴가 아니라 환경설정 하위에 배치해야 한다.
2. WHEN 카테고리가 하나도 없는 신규 사용자면 THEN 시스템은 기본 카테고리 "할일"을 자동으로
   생성해 빈 격자를 피해야 한다.

---

## 요구사항 16 — 월간 뷰 카테고리 필터

**사용자 스토리:** 사용자로서, 월간 개요에서 특정 카테고리만 골라 보고 싶다.

### 수용 기준
1. 시스템은 월간 뷰에서 표시할 카테고리를 다중 선택하는 필터를 제공해야 한다.
2. 필터는 표시에만 영향을 주며 데이터를 변경하지 않는다.
3. 필터를 모두 해제하면(또는 기본 상태) 전체 카테고리를 표시해야 한다.

---

## 요구사항 17 — 환경설정 확장 & 경량 피드백

**사용자 스토리:** 사용자로서, 설정을 한곳에서 풍성하게 다루고, 문의/의견을 남기고 싶다.

### 수용 기준
1. 시스템은 환경설정을 한곳에 모아야 한다: 하루 경계 시각, 기본 뷰, 카테고리 관리,
   CSV 내보내기, (선택) 테마.
2. 시스템은 사용자가 문의/의견을 남길 수 있는 경량 피드백 폼을 제공해야 한다(저장은 DB 테이블).
3. 전면 티켓/상담 시스템(고객센터)은 범위 밖이다.
